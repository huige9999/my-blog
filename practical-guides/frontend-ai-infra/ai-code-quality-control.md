## 1. AI 生成代码最大的问题

AI 写代码很快，但快不等于好。

如果缺少质量控制，AI 可能制造新的问题：

- 看似可运行，但隐藏 bug
- 代码风格不一致
- 重复逻辑变多
- 类型写得很松
- 过度封装
- 乱改公共模块
- 忽略边界情况
- 引入安全风险
- 破坏原有架构

所以 AI 工程化的重点不是"生成代码"，而是"控制生成代码的质量"。

## 2. 人类不能放弃架构控制权

AI 适合做执行，但不适合完全替代架构判断。

人类应该控制：

- 需求理解
- 方案选择
- 改动边界
- 架构方向
- 质量标准
- Review 结果
- 发布风险

可以把 AI 当成高效执行者，而不是最终负责人。

## 3. AI 代码 Review 重点

Review AI 生成代码时，可以重点看这些方面。

### 3.1 是否满足需求

先看功能是否真正满足需求，而不是只看代码是否漂亮。

### 3.2 是否符合项目规范

包括：

- 目录规范
- 命名规范
- 组件使用规范
- 接口封装规范
- 状态管理规范
- 样式规范

### 3.3 是否改动范围过大

AI 有时会顺手重构。要警惕：

- 无关文件被修改
- 公共组件被改动
- 全局样式被调整
- 原有逻辑被重写

### 3.4 是否有类型问题

重点看：

- any 是否过多
- 类型是否准确
- 接口返回类型是否可信
- 可空值是否处理
- 联合类型是否覆盖完整

### 3.5 是否处理异常状态

包括：

- loading
- empty
- error
- 接口失败
- 表单校验失败
- 重复提交
- 权限不足
- 数据为空

## 4. 质量门禁

质量控制不能只靠肉眼。

可以引入自动化门禁：

- TypeScript 类型检查
- ESLint
- Prettier
- 单元测试
- 组件测试
- 构建检查
- Git Hook
- CI 检查

至少要保证：

```bash
pnpm typecheck
pnpm lint
pnpm build
```

能够通过。

## 5. 让 AI 自查

AI 生成代码后，可以要求它自查。

例如：

```txt
请对刚才的改动做一次自查：
1. 是否存在未定义变量
2. 是否存在未使用变量
3. 是否有 TypeScript 类型风险
4. 是否有和项目规范不一致的地方
5. 是否处理了 loading、empty、error 状态
6. 是否有不必要的重构
7. 是否有潜在副作用
```

如果工具环境支持，还可以让它根据命令输出修复问题。

## 6. 建立 AI Review Checklist

可以为项目准备一份清单。

```md
# AI 代码 Review Checklist

## 需求

- [ ] 功能是否完整
- [ ] 交互是否符合预期
- [ ] 边界状态是否处理

## 工程规范

- [ ] 是否符合目录规范
- [ ] 是否使用项目封装组件
- [ ] 是否使用项目接口封装
- [ ] 是否遵守命名规范

## 类型和和质量

- [ ] 是否有 any 滥用
- [ ] 是否有类型遗漏
- [ ] 是否通过 typecheck
- [ ] 是否通过 lint
- [ ] 是否通过 build

## 风险

- [ ] 是否修改了无关文件
- [ ] 是否影响公共组件
- [ ] 是否影响全局样式
- [ ] 是否存在权限或安全问题
```

这份清单既可以给人用，也可以给 AI 用。

## 7. 避免 AI 制造重复代码

AI 很容易复制粘贴相似逻辑。

比如多个页面重复写：

- 查询参数处理
- 分页逻辑
- 弹窗状态
- 表单重置
- 删除确认

如果这些模式稳定，可以考虑沉淀成：

- hooks
- composables
- 业务组件
- 页面模板
- Skill

但注意不要过早抽象。先识别重复，再逐步沉淀。

## 8. 避免过度封装

AI 有时会为了"优雅"而过度封装。

常见问题：

- 小需求拆太多文件
- 简单逻辑抽复杂 hook
- 为一次性场景写通用组件
- 把业务代码抽得难以追踪

Review 时要判断：

> 这个抽象是否真的降低了复杂度，还是只是把复杂度搬到了别处？

## 9. 保持小步提交

AI 改代码时，最好保持小步提交：

- 一个任务一个改动范围
- 一次只解决一个问题
- 先实现主流程
- 再补状态和优化
- 最后做清理和自查

不要一次让 AI 同时做新增页面、重构组件、调整样式、改接口封装。

任务越大，风险越高。

## 10. 小结

AI 代码质量控制的核心是：

```txt
明确边界
自动检查
人工 Review
持续沉淀
```

AI 能提高编码速度，但质量来自工程体系。

如果没有上下文、规则、检查和 Review，AI 只是更快地制造混乱。

如果有良好的质量控制，AI 才能成为真正的工程生产力。
