## 1. 为什么 AI 编程不能只靠一句话

很多人使用 AI 编程时，会直接输入：

```txt
帮我写一个用户管理页面
```

然后发现 AI 生成的代码经常有问题：

- 组件用错
- 接口瞎编
- 状态管理方式不符合项目
- 目录结构不一致
- 样式风格不统一
- 逻辑看似能跑，但不符合业务规则
- 改动范围过大，甚至破坏原代码

原因不是 AI 完全不行，而是它缺少上下文。

AI 不知道你的项目结构、不知道组件库规则、不知道接口约定、不知道团队代码风格。你只给它一个任务，它只能根据通用经验猜。

## 2. 什么是上下文工程

上下文工程就是：

> 有意识地组织、筛选、提供 AI 完成任务所需要的信息。

它不是简单把所有代码都塞给 AI，而是让 AI 在合适的时间看到合适的信息。

对前端项目来说，上下文通常包括：

- 当前需求背景
- 项目技术栈
- 目录结构
- 相似页面代码
- 组件库文档
- 接口定义
- 状态管理方式
- 路由规则
- 权限规则
- 代码风格
- 修改边界
- 验收标准

## 3. AI 胡写的本质

AI 胡写通常来自三个原因。

### 3.1 缺少事实

比如没有接口文档，它就会编接口。

### 3.2 缺少约束

比如没有告诉它不要改公共组件，它可能顺手改掉底层逻辑。

### 3.3 缺少示例

比如没有提供相似页面，它就会按通用模板写，而不是按你的项目风格写。

所以提升 AI 代码质量的第一步不是写更玄妙的 prompt，而是补齐上下文。

## 4. 项目上下文应该包含什么

可以为每个项目准备一份 `PROJECT_CONTEXT.md`。

内容可以包括：

```md
# 项目上下文

## 技术栈

- Vue 3
- TypeScript
- Vite
- Pinia
- Vue Router
- Element Plus

## 目录结构

- src/pages：页面
- src/components：通用组件
- src/api：接口封装
- src/stores：状态管理
- src/router：路由配置

## 代码约定

- 使用 Composition API
- 统一使用 `<script setup lang="ts">`
- 接口请求统一放在 src/api
- 禁止在页面中直接写 axios
- 表格统一使用项目封装的 BaseTable
- 表单统一使用 BaseForm

## 修改边界

- 未明确要求，不允许修改公共组件
- 未明确要求，不允许修改全局样式
- 修改前先阅读相似页面
```

这类文档对人有用，对 AI 也有用。

## 5. 任务上下文应该包含什么

除了项目长期上下文，每次任务还要补充任务上下文。

例如：

```md
# 当前任务

## 需求

新增一个用户管理页面，支持用户列表查询、新增、编辑、删除。

## 接口

- GET /api/users：查询用户列表
- POST /api/users：新增用户
- PUT /api/users/:id：编辑用户
- DELETE /api/users/:id：删除用户

## 参考页面

请参考 `src/pages/role/index.vue` 的表格、搜索、弹窗写法。

## 组件要求

- 表格使用 BaseTable
- 表单使用 BaseForm
- 弹窗使用 BaseDialog

## 验收标准

- 支持 loading
- 支持 empty
- 删除前有二次确认
- TypeScript 无报错
- 不修改公共组件
```

这比一句"帮我写页面"稳定得多。

## 6. 让 AI 先理解再执行

一个很重要的实践是：

> 不要一上来就让 AI 改代码，先让它阅读和复述。

可以这样要求：

```txt
先不要修改代码。
请先阅读以下文件，说明这个页面的结构、数据流、组件使用方式和你准备如何实现。
等我确认后再开始修改。
```

这个流程能减少很多误改。

AI 的第一轮输出应该是理解和计划，而不是直接动手。

## 7. 限制 AI 的修改范围

AI 编程最怕"顺手重构"。

所以任务里要明确：

- 只允许修改哪些文件
- 不允许修改哪些文件
- 是否允许新增文件
- 是否允许调整公共组件
- 是否允许改接口封装
- 是否允许重构旧逻辑

例如：

```txt
本次只允许修改：
- src/pages/user/index.vue
- src/api/user.ts

禁止修改：
- src/components
- src/router
- src/styles
```

修改边界越清晰，结果越可控。

## 8. 提供相似代码比解释更有效

AI 很擅长模仿模式。

与其长篇解释项目风格，不如提供一个相似页面作为参考。

例如：

```txt
请参考 src/pages/role/index.vue 的写法实现用户管理页面。
包括：
1. 搜索表单结构
2. 表格列配置
3. 弹窗表单写法
4. 接口调用方式
5. loading 和分页处理
```

相似代码是高价值上下文。

## 9. 上下文不是越多越好

上下文工程不是把全部项目都丢给 AI。

太多无关上下文会带来问题：

- AI 抓不住重点
- 输出变慢
- 容易混淆旧逻辑
- 成本更高
- 更难控制修改边界

好的上下文应该满足：

- 和当前任务直接相关
- 足够支撑决策
- 有明确优先级
- 有清晰边界

## 10. 小结

AI 编程的核心不是"许愿"，而是上下文工程。

可以记住这句话：

> AI 代码质量 = 模型能力 × 上下文质量 × 约束清晰度 × 人类 Review 能力。

在真实项目里，真正拉开差距的不是谁会写更花的 prompt，而是谁能把项目知识、业务规则、组件规范、工程流程组织成 AI 能理解和执行的上下文。
