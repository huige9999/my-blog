## 1. 为什么要区分 Prompt、Rules、Skill

使用 AI 编程时，很多人会把所有指令都叫 prompt。

但在工程化场景下，临时指令、长期规则、可复用流程应该分开管理。

可以简单理解为：

```txt
Prompt：这一次我要你做什么
Rules：在这个项目里你一直要遵守什么
Skill：遇到某类任务时你应该按什么流程做
```

这三者分清楚后，AI 编程会更稳定，也更容易沉淀。

## 2. Prompt：临时任务指令

Prompt 是一次性的任务说明。

例如：

```txt
请帮我实现用户管理页面，包含查询、新增、编辑、删除功能。
参考 src/pages/role/index.vue 的写法。
```

Prompt 的特点：

- 面向当前任务
- 临时性强
- 可以很具体
- 不一定需要长期保留

适合放在 Prompt 里的内容：

- 当前需求
- 当前要修改的文件
- 当前参考页面
- 当前验收标准
- 当前限制条件

## 3. Rules：项目长期约束

Rules 是项目级或团队级长期规则。

例如：

```md
# AI 编码规则

- 所有 Vue 文件使用 `<script setup lang="ts">`
- 接口请求必须封装在 src/api 中
- 页面中禁止直接使用 axios
- 表格统一使用 BaseTable
- 弹窗统一使用 BaseDialog
- 未明确要求，不允许修改公共组件
- 修改代码前先阅读相似页面
```

Rules 的特点：

- 长期有效
- 多个任务共享
- 用来约束 AI 行为
- 越稳定越适合沉淀

适合沉淀成 Rules 的内容：

- 技术栈规范
- 目录规范
- 命名规范
- 组件使用规范
- 样式规范
- 禁止事项
- 代码风格
- 质量要求

## 4. Skill：可复用任务流程

Skill 是针对某类任务的标准执行流程。

例如"新增管理后台 CRUD 页面"可以沉淀成 Skill：

```md
# Skill：新增管理后台 CRUD 页面

## 适用场景

当需要新增列表查询、新增、编辑、删除类后台页面时使用。

## 执行步骤

1. 阅读需求和接口文档
2. 查找相似页面
3. 总结相似页面的数据流、组件使用方式
4. 设计页面结构
5. 新增接口封装
6. 实现列表查询
7. 实现新增和编辑弹窗
8. 实现删除二次确认
9. 补充 loading、empty、error 状态
10. 自查 TypeScript、Lint 和构建问题

## 约束

- 不允许绕过项目封装组件
- 不允许直接在页面中写请求库
- 不允许擅自修改公共组件
```

Skill 的特点：

- 面向一类任务
- 可重复使用
- 带有步骤
- 带有输入输出
- 可以持续优化

## 5. 三者的关系

可以用一个例子理解。

你要让 AI 新增一个用户管理页面。

### Prompt

```txt
请新增用户管理页面，字段包括姓名、手机号、角色、状态。
接口参考下面文档。
```

### Rules

```txt
必须使用 BaseTable、BaseForm、BaseDialog。
接口请求必须写在 src/api。
页面使用 Vue 3 + TypeScript + script setup。
```

### Skill

```txt
按照"新增管理后台 CRUD 页面"的流程执行：
先读相似页面，再出方案，确认后编码，最后自查。
```

Prompt 负责当前任务，Rules 负责长期边界，Skill 负责执行流程。

## 6. 什么时候从 Prompt 沉淀成 Rules

当某条指令频繁出现，而且长期稳定，就适合变成 Rules。

例如你每次都要说：

```txt
不要直接用 axios，请使用项目封装的 request。
```

那它就应该进入 Rules。

判断标准：

- 是否经常重复说
- 是否长期有效
- 是否适用于多个任务
- 是否能避免常见错误

## 7. 什么时候从 Prompt 沉淀成 Skill

当你发现一类任务有稳定步骤时，就适合变成 Skill。

例如：

- 新增 CRUD 页面
- 修复线上 bug
- 重构组件
- 接入新接口
- 编写单测
- 优化性能
- 生成组件文档

这些任务不是一句规则能描述清楚的，而是需要流程。

## 8. Skill 应该怎么写

一个好的 Skill 至少包含：

- 适用场景
- 输入信息
- 执行步骤
- 输出结果
- 约束条件
- 自查清单
- 常见错误

例如：

```md
# Skill：修复前端 Bug

## 适用场景

用户提供 bug 描述、报错信息或复现步骤时使用。

## 输入

- bug 描述
- 复现步骤
- 相关文件
- 报错日志
- 期望结果

## 步骤

1. 先复述 bug 现象
2. 定位可能影响范围
3. 阅读相关代码
4. 给出原因分析
5. 提出修复方案
6. 修改最小范围代码
7. 说明验证方式

## 自查

- 是否修复根因
- 是否引入副作用
- 是否影响其他页面
- 是否需要补充测试
```

## 9. 个人如何管理这些沉淀

可以在项目里建一个目录：

```txt
.ai/
├── rules.md
├── context.md
└── skills/
    ├── crud-page.md
    ├── bugfix.md
    ├── refactor-component.md
    └── code-review.md
```

也可以放在个人知识库里，按项目复制使用。

重点不是形式，而是让它们能被复用。

## 10. 小结

Prompt、Rules、Skill 是 AI 工程化的三个层次：

```txt
Prompt：临时意图
Rules：长期约束
Skill：可复用流程
```

真正的 AI 工程化，不是每次都重新写一大段提示词，而是把高频经验沉淀成 Rules 和 Skill。

这就是从"会用 AI"到"会建设 AI 工作流"的关键一步。
