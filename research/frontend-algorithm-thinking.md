> 面对复杂系统时，不试图一口吃掉整体，而是先拆出可控局部，定义状态、实现最小单元，再逐步组合成整体。

这篇文章不是讲 LeetCode 模板，而是梳理一种思维方式——**把复杂问题转成结构化问题，拆成可验证局部，再通过规则组合成最终结果**。以下六种算法思维贯穿其中。

---

## 一、分治思维：庞然大物先拆成局部

看到最终效果时，算法思维会问三件事：

1. **这个大效果能不能拆成几个小效果？**
2. **每个小效果能不能独立完成？**
3. **最后它们怎么合并？**

以一个复杂活动页为例：

```
页面整体入场
  ├─ 背景渐变/粒子动画
  ├─ 标题缩放进入
  ├─ 卡片列表 stagger 依次出现
  ├─ 按钮呼吸动画
  └─ 滚动触发某些元素动效
```

正确做法不是直接写"整个页面动画"，而是逐个击破：静态页面 → 标题动画 → 卡片动画 → 按钮动画 → 统一编排时序。

---

## 二、状态思维：先定义局面，再定义变化

复杂动画的本质是一组**状态变化**，而不是一堆 CSS/JS 代码。

一个元素可能经历的状态：`hidden → entering → visible → hovering → leaving`。

```js
const states = {
  hidden:  { opacity: 0, transform: 'translateY(20px) scale(0.95)' },
  visible: { opacity: 1, transform: 'translateY(0) scale(1)' }
}
```

核心逻辑：**状态定义 → 状态转移 → 动画表现**。这与动态规划、状态机、BFS/DFS 共享同一个底层习惯——先定义当前局面，再定义局面如何变化。

---

## 三、迭代思维：先做静态，再逐步增强

不要追求一步到位，每轮让系统更接近最终答案：

| 轮次 | 目标 |
|------|------|
| 第 1 轮 | 页面静态结构能看 |
| 第 2 轮 | 基础样式正确 |
| 第 3 轮 | 单个元素动画正确 |
| 第 4 轮 | 多个元素动画能组合 |
| 第 5 轮 | 整体时序和交互补齐 |

前端尤其需要这种方式——复杂效果脑补不完整，必须通过**可运行的中间态**不断校正。

---

## 四、最小单元思维：先造螺丝，再组装

先解决一个最小子问题，复用它解决更大的问题：

```
FadeIn 组件 → ScaleIn 组件 → StaggerList 组件 → 组合成页面
```

```tsx
<ScaleIn><Title /></ScaleIn>
<StaggerList>{cards.map(card => <Card />)}</StaggerList>
```

每个"螺丝"都是可验证模块。巨大组件里任何一个地方错了，你不知道是布局、状态、时序还是动画曲线的问题——拆小了才好定位。

---

## 五、自底向上思维：从局部拼出整体

```
底层：单个元素动画
中层：一组元素动画
上层：区域动画
顶层：页面整体动画编排
```

实战中通常混合使用：**先自顶向下粗拆结构 → 再自底向上实现局部 → 最后回到顶层整合**。

选择下手顺序时，优先选：最独立的模块、最容易验证的模块、最核心的不确定点、最能带来信心的模块。

---

## 六、组合思维：难点不在堆代码，而在编排关系

最后合并时，真正要处理的是"调度问题"：

- 谁先动？谁后动？
- 哪些并行？哪些串行？
- 哪些受滚动/交互控制？
- 哪些只播一次？哪些可重复？

```
页面进入 → 背景先出现 → 标题 200ms 后出现 → 卡片依次出现 → 按钮最后呼吸
```

复杂动画本质上就是一组"视觉任务"的调度。

---

## 实战模板：复杂效果拆解八步法

遇到复杂动画页面，按以下顺序思考：

1. **静态结构拆分** — 页面有哪些区域？哪些组件？
2. **状态拆分** — 每个区域有哪些状态？hidden / visible / active / leaving？
3. **动画拆分** — 每个元素从什么状态变到什么状态？
4. **触发条件拆分** — 页面加载？滚动？点击？hover？
5. **时序拆分** — 哪些串行？哪些并行？是否需要延迟？
6. **最小单元实现** — 先单独实现一个元素/区域的动画
7. **组合编排** — 把小动画合成页面级动画
8. **回归调整** — 调时间、缓动、层级、性能

---

## 小结

前端复杂效果的拆解，本质上是五种算法思维的工程化应用：

> **分治 + 状态建模 + 迭代逼近 + 自底向上组合 + 调度编排**

它不一定表现为 LeetCode 里的某个模板，但背后的思考方式完全一致：**把复杂问题转成结构化问题，把不可控整体拆成可验证局部，再通过规则组合成最终结果。**
