# 代码阅读的六视角框架：从混乱到系统的阅读方法

## 核心问题

读代码时最大的困难不是"不会读"，而是**观察角度太多，不知道该从哪里切入**。解决方案是给代码阅读建立分层框架，不要把所有问题平铺，而是按视角逐层展开。

## 六个阅读视角

| 视角 | 核心问题 | 解决什么 |
|------|---------|---------|
| 业务视角 | 这个模块解决什么业务问题？ | 防止陷入代码细节而忘了目标 |
| 入口视角 | 代码从哪里开始跑？ | 确定追踪起点，避免越读越散 |
| 流程视角 | 一条操作链路怎么走？ | 理解功能完整运行过程 |
| 状态视角 | 有哪些关键状态？如何变化？ | 发现脏状态、竞态、不同步问题 |
| 数据视角 | 数据结构是什么？如何流转？ | 理解数据的来源、加工和去向 |
| 架构视角 | 模块之间怎么协作？ | 判断分层是否合理、边界是否清晰 |

一句话总结它们的关系：

> **流程**是时间线，**状态**是变化点，**数据**是载体，**模块关系**是空间结构，**分层**是抽象结果，**业务**是原因。

## 每个视角要看什么

### 1. 业务视角 — 先别看代码

问三个问题：
- 用户在这里完成什么任务？有哪些核心操作？
- 有哪些业务规则和约束？
- 成功/失败的结果分别是什么？

### 2. 入口视角 — 找到起点

入口通常有四类：
- **生命周期入口**：`onMounted`、`created`、`useEffect`
- **路由入口**：路由参数、query、`beforeRouteEnter`
- **用户事件入口**：按钮点击、表单提交、搜索、分页
- **外部入口**：接口回调、WebSocket、定时器、权限变化

找到入口后，按入口逐条追踪，就不会散。

### 3. 流程视角 — 追踪完整链路

按"用户动作 → 状态变化 → 接口调用 → UI 更新"的结构读，并且追问：
- 这一步改变了什么状态？
- 失败了会怎么样？
- 是否存在竞态或重复刷新？

### 4. 状态视角 — 列状态表

为每个关键状态追问：
- 在哪里初始化、赋值、读取、重置？
- 多个状态之间是否有关联？
- 有没有脏状态或不同步的风险？

### 5. 数据视角 — 画数据流

关注数据的三种形态：
- **后端返回的原始结构**
- **前端加工后的内部结构**
- **提交给后端的请求结构**

重点看数据转换的位置、方式和边界情况。

### 6. 架构视角 — 看角色分工

一个页面通常拆为：页面层、组件层、接口层、工具层、状态层、路由层。判断业务逻辑是否过度集中在页面里，哪些逻辑可以抽象复用。

## 三遍读法

实际阅读时**不要一次性打开所有视角**，而是分三遍：

| 遍数 | 关注点 | 目标产出 |
|------|--------|---------|
| 第一遍：读骨架 | 模块干嘛的、有哪些入口、有哪些接口和主流程 | 流程图 |
| 第二遍：读状态和数据 | 关键状态、数据结构、状态转移、数据加工 | 状态表 + 数据流 |
| 第三遍：读设计和问题 | 模块分层、耦合点、重复逻辑、风险点 | 架构判断 + 优化建议 |

## 配合 AI Agent 使用的提示词

```
请基于当前代码，按以下 8 个维度分析这个模块：
1. 业务问题
2. 入口
3. 主流程
4. 状态
5. 数据结构
6. 模块关系
7. 副作用
8. 可优化点

要求：
- 每个结论都要对应到具体代码位置
- 不确定的地方标注"待确认"
- 不要脑补不存在的逻辑
- 最后输出一份可以手动验证的检查清单
```

## 总结

这套框架的本质是将"读代码"升级为以下能力训练：

- 代码 → 业务流程
- 代码 → 状态机
- 代码 → 数据流
- 代码 → 模块依赖图
- 代码 → 分层架构图

不是"看代码在写什么"，而是**通过代码理解系统的设计意图**。
