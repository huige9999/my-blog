## 核心观点

AI 时代开发者的角色从"写代码的人"变成"组织需求、约束、上下文，让 AI 去执行的人"。这不是 prompt 魔法，而是一套新的软件工程流程。

## 1. Spec Driven：先说清楚要什么，再让 AI 写

以前的做法是"我想做个活动运营平台 → AI 帮我写代码"，现在应该是：

```
定义 MVP → 定义页面流 → 定义数据模型 → 定义接口边界
→ 定义开发规范 → 定义验收方式 → 再让 AI 分阶段实现
```

## 2. 约束比 prompt 花活更重要

AI 不是万能程序员，而是需要你制定团队规范的成员。三层约束：

- **技术约束**：技术栈、架构风格、代码组织方式
- **工程约束**：每次只做一个小任务、修改前先读相关文件、不确定时先提问
- **质量约束**：能启动、核心流程可验证、有验收清单

## 3. 验证能力是分水岭

AI 写完代码 ≠ 合格。任务描述应该包含验证标准：

```
实现登录功能：
1. 前端登录页可输入账号密码
2. 调用 POST /auth/login
3. 登录成功后保存 token 并跳转首页
4. 登录失败展示错误提示
5. 给出手工测试步骤
6. 确认 dev 无报错
```

> 真正高级的不是"让 AI 写代码"，而是"让 AI 写完后知道怎么证明它是对的"。

## 4. 角色转变：从执行者到指挥者

重点练的不是更多语法，而是：

```
定义任务边界 → 定义输入上下文 → 定义输出格式
→ 定义验收标准 → 定义失败回滚方案 → 定义文档沉淀位置
```

## 5. MCP 不要迷信

MCP 给 AI 接外部能力，但常驻上下文、消耗 token。现阶段更高 ROI 的是：
先把项目文档（context、rules、tasks）组织好，再谈工具扩展。**先会组织上下文，再谈 MCP。**

## 6. 用 AI 练架构能力

看到任何产品，主动拆解：解决什么问题 → 模块怎么拆 → 核心数据流 → 技术难点 → AI 做个 POC。拿真实产品训练自己（Notion 块编辑器、飞书多维表格等），比听课更能长架构感。

## 7. 前端设计：给 design token，不让 AI 猜

不要说"帮我做一个好看的后台首页"，而是：

```
参考 Linear / Vercel 的风格：
- 留白充足、卡片圆角 12px
- 字号层级清晰、主色低饱和
请先输出 design token，再实现页面。
```

## 我要落实的闭环

```
想法 → 文档 → 任务 → AI 执行 → 验证 → 复盘 → 沉淀
```
